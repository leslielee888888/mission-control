Mission Control — architecture & stack

How the pieces fit together and why each library was chosen. Full requirements live in docs/prd/mission-control.md; this page is the fast read.

Mission Control is one API with three clients. A CLI and a minimal web UI both talk to the same FastAPI service over HTTP — neither reads the database directly, and neither gets its own copy of business logic. The API is layered (routes → services → models) so the rules that matter — tenant isolation, the approval gate, the matcher — live in exactly one place.

Stack, and why

Backend
  • FastAPIType-hinted routes, automatic OpenAPI — the schema the SPA's typed client is generated from.
  • SQLModelSQLAlchemy + Pydantic in one model — one class defines the table and the validation.
  • SQLiteGenuinely relational domain (orgs, crew, missions, requirements, assignments with real foreign keys) — no external service to install for a take-home.
  • pytestRepresentative cases over the vertical slice, not exhaustive suites — see the coverage boundary below.
  • bcryptPassword hashing for the real login endpoint — see the auth note below.
Frontend (showcase)
  • React + ViteFast dev loop for a handful of screens — no framework machinery this build doesn't need.
  • React QueryServer state — loading/error/stale states and cache invalidation on mutation, which is the whole point of the showcase.
  • Generated typed clientFrom FastAPI's OpenAPI schema — calls read as api.mission.approve(id), RPC-flavored, no second protocol.
  • useStateLocal UI state only — no Redux/Zustand for three screens.
  • Tailwind CSSUtility classes are fast for 2-3 screens — no component stylesheet to maintain past this showcase.
CLI
  • TyperPairs naturally with FastAPI's type hints and Pydantic schemas — same mental model, both ends.
  • httpxThe CLI's HTTP client — every command is a real request, never a DB shortcut.
  • missionctlSystem of record for full workflow coverage; JSON output, pretty-printed.

How a request moves through the system

Decisions worth knowing before you read the code

Vertical slice

Not every FR is built to the same depth. Real and tested: auth/RBAC/tenant isolation, the mission lifecycle and its approval gate, the matcher, and assignments — one coherent story: create a mission, match it, propose, accept, approve. Lighter or mocked where time is short: crew self-service CRUD (profile, skills, availability). This isn't laziness — it's what "vertical slice over breadth" (the brief's own words) actually means once you commit to it.

Auth

One real login endpoint, POST /auth/login (email + password, hashed at rest), issues an opaque bearer token. Both clients hit the exact same endpoint — the CLI's login command and the SPA's login form are two front doors on one mechanism, not two auth systems to maintain.

Matcher

Two passes per requirement. Hard filter — skill at proficiency, no date overlap, no conflicting confirmed assignment — removes anyone who can't do the job. Weighted score ranks who's left: proficiency surplus 50%, workload 30%, availability margin 20%, each normalized 0–1. Every eligible candidate comes back, not just a top few — explainability was a stated evaluation criterion, so the reasoning has to be visible, not just the ranking.

Tenant isolation

Structural, not just tested: every data-access function takes org_id as a required argument. A query that could span two organisations' data isn't a bug waiting to be caught by a test — it's a function signature that doesn't compile.
